# Native model reference probes

`ProbeTeams.java` is an original wire-reference probe for the pinned server's
`ClientboundSetPlayerTeamPacket.STREAM_CODEC`. Compile it with the verified server
export classpath and run `ProbeTeams`. The small retained packet fixture covers
create/update/remove/join/leave; it pins the current component/visibility/collision/
optional-colour/options ordering, which differs from older protocol descriptions.
These are codec observations, not graphical or public-server acceptance.

`ProbePlayerLabels.java` queries the pinned Avatar pose dimensions and NAME_TAG
attachments. The current standing/crouching attachment heights are native facts;
the shared label constructor must not apply its older camera-space sneak drop
again. Inspect `SubmitNodeCollection.submitNameTag` for the additional world-space
clearance. The probe establishes CPU placement inputs, not visible output.

These small original probes call the verified target client's public model API. They do
not ship Minecraft code, textures, or generated model data. Use only the Java version
and archive hashes pinned in `crates/java-protocol/data/target.json`.

For head geometry, set `JAVA_HOME` to JDK 25 and `JAVA_REFERENCE_CP` to the verified
client JAR plus its verified dependencies (including the server export libraries):

```sh
mkdir -p .local/java-reference
"$JAVA_HOME/bin/javac" -cp "$JAVA_REFERENCE_CP" -d .local/java-reference tools/java-reference/ExportHeadVertices.java
"$JAVA_HOME/bin/java" -cp ".local/java-reference:$JAVA_REFERENCE_CP" ExportHeadVertices > .local/java-reference/head-vertices.txt
CINNABAR_JAVA_HEAD_VERTICES="$PWD/.local/java-reference/head-vertices.txt" cargo test -p render-model pinned_native_model_vertices_and_uvs --lib
```

The probe exercises the target's actual baked models and animation methods at three
phases and three rotations. The Rust test compares both directions of the position/UV
set, allowing only floating-point tolerance and quad-to-triangle duplication. These are
CPU model comparisons, not rendered acceptance. Keep generated data out of Git.

For copper statues, compile `ExportStatueVertices.java` alongside the head probe and
run it with the same verified classpath. Save its output to an untracked file and set
`CINNABAR_JAVA_STATUE_VERTICES` plus `CINNABAR_JAVA_TEST_ASSETS` (the prepared runtime
directory) for `cargo test -p render-model java_statue --lib`. It compares all four poses
and four facings, including outward normals, then checks negative-coordinate translation.
The production model hierarchy is generated by the existing `assetc java-prepare` /
`java-entities` workflow; the probe is only an independent expectation, not runtime data.

`ExportPotVertices.java` captures all seven decorated-pot model parts under each native
facing transform. Compile it alongside `ExportHeadVertices.java` and
`ExportStatueVertices.java` with the same pinned classpath, then pass its output as
`CINNABAR_JAVA_POT_VERTICES`. Zero-thickness top/bottom cubes contain collapsed edge
quads; the native GPU rasterizes none of their area. Tests compare every nondegenerate
reference quad and the shared hierarchy emitter omits the collapsed faces.
`InspectPotPatterns.java` inspects the actual vanilla item component initializers against
`VanillaRegistries.createWorldLookup`; pass its output as `CINNABAR_JAVA_POT_ITEMS`.
It verifies every default pottery-pattern mapping and the positive/negative wobble duration.

`ExportConduitVertices` captures native ModelPart positions, UVs and normals for
the inactive shell and all active draw transforms, including the three wind
orientations and pitched/yawed eye. It compiles with `ExportHeadVertices` and
`ExportStatueVertices`; set `CINNABAR_JAVA_CONDUIT_VERTICES` for the native geometry
fixture. Model factories and transforms were inspected from the verified 26.3
ConduitRenderer; no proprietary model data is committed.

`InspectPortal.java` prints the pinned native pipeline layer counts, exposed faces and
transformed portal bounds. Compile/run against the verified client and its extracted
libraries as above; compare these observations with native portal geometry tests.

`InspectGateway.java` compares every pinned state's native gateway face visibility
against full-face shape identity. `ExportGatewayVertices.java` invokes the native
BeaconRenderer through a capture-only SubmitNodeCollector for three clocks/scales and
both beam materials. Its output feeds `CINNABAR_JAVA_GATEWAY_VERTICES`; these are CPU
reference observations, not screenshots or live gameplay.

`InspectMovingPiston.java` samples the real pinned entity's progress and offsets for
six directions, extension/retraction and partial ticks, without a world or renderer.
Compile with the verified reference classpath and run `InspectMovingPiston > motion.txt`;
set `CINNABAR_JAVA_PISTON_MOTION` to that file for the simulation regression. Model-plan
tests take `CINNABAR_JAVA_PISTON_BLOCKS` pointing to the verified pinned `blocks.json`.
These are CPU behavior fixtures; they do not establish moving-piston rendering or gameplay.

`NativeMenuFixture.java` opens the pinned vanilla `ChestMenu` for each of its six
row counts, using `ServerPlayer.openMenu`. It is an opt-in admin fixture on an
isolated offline server, **not unmodified-vanilla qualification or Hypixel evidence**.
Vanilla still owns slot rules, revisions, accepted/rejected clicks and carried
items; the fixture sends no replacement protocol responses. It instruments one
server tick to poll a local file once per 20 ticks, accepting only `open 1` through
`open 6`, `dump`, or the read-only `players` pose/bounds/health query. Never install it on a public server or normal user world.

```sh
mkdir -p .local/java-menu-fixture/classes
"$JAVA_HOME/bin/javac" --release 25 -d .local/java-menu-fixture/classes tools/java-reference/NativeMenuFixture*.java
printf 'Manifest-Version: 1.0\nPremain-Class: NativeMenuFixture\nAgent-Class: NativeMenuFixture\nCan-Retransform-Classes: true\n' > .local/java-menu-fixture/MANIFEST.MF
"$JAVA_HOME/bin/jar" cf .local/java-menu-fixture/fixture-bridge.jar -C .local/java-menu-fixture/classes NativeMenuFixtureBridge.class
"$JAVA_HOME/bin/jar" cfm .local/java-menu-fixture/fixture.jar .local/java-menu-fixture/MANIFEST.MF -C .local/java-menu-fixture/classes NativeMenuFixture.class -C .local/java-menu-fixture/classes 'NativeMenuFixture$1.class'
```

Start the existing controlled server from its disposable world directory with
`-javaagent:/absolute/path/fixture.jar=/absolute/path/request,FixturePlayer` before
its normal `-jar .../server.jar nogui` arguments. Connect the actual native client,
write `open 4` to that request file, then use normal UI input. `dump` logs the
server's actual nonempty slots and carried stack. The bridge JAR must be beside
the agent JAR. Remove the JVM agent argument on restart to restore the unmodified
server. No proprietary binaries or generated worlds belong in Git.

`ProbePlayerPosture.java` calls the pinned wide/slim `PlayerModel.setupAnim` for
standing/crouching and three gait samples. It also records root transforms. Compile
with the same verified client/server-library classpath as the entity exporter; run
`ProbePlayerPosture /absolute/path/postures.json` to write clean JSON without native
log prefixes. Set `CINNABAR_JAVA_PLAYER_POSTURES` to that file for the owning world
posture test. These are CPU reference vectors, not rendered acceptance. The unit-scale
crouch world offset (-2/16) comes separately from the verified `AvatarRenderer.getRenderOffset`.

`ProbeEntityTargeting.java` encodes the pinned native attack packet, reads standing/
crouching avatar dimensions, and samples `AABB.clip`/`contains` with original synthetic
rays. Compile with that verified classpath and run
`ProbeEntityTargeting /absolute/path/targeting.json`. The `corpus` field supplies
`sim/java/entity_selection/reference.json` cases; the fixture records its box and provenance.
The maximum-face inside-origin and segment-end cases must remain misses. These are CPU
reference vectors, separate from native GUI/server-authoritative damage acceptance.

`NativeMotionCounters.java` composes a read-only observer with the opted-in fixture's
existing bootstrap callback. It samples the actual vanilla listener's server-tick and
received-movement counters; it neither replaces packets nor changes player/world state.
Use only the isolated acceptance JVM. Compile it with JDK25, package its class with
`Premain-Class: NativeMotionCounters` and `Agent-Class: NativeMotionCounters`, then attach:

```sh
"$JAVA_HOME/bin/java" --add-modules jdk.attach -cp /absolute/path/motion.jar NativeMotionCounters SERVER_PID /absolute/path/motion.jar /absolute/path/motion-request
printf sample > /absolute/path/motion-request
```

The callback consumes the dedicated request file at most once per second. Capture a
second `sample` after further real client ticks; compare counter deltas while stationary,
then exercise walking/jumping and corrections. `detach` restores the prior callback.
Without attach access, place its `-javaagent:...=.../motion-request` after the existing
menu-fixture agent argument on the controlled server's next clean startup. Counter
observations establish packet cadence only; they do not prove complete movement,
knockback, public-server or graphical parity. Do not use a normal user's file as a request.

`ExportInventoryFacts.java` exports schema3 of the pinned inventory facts: registry
identity, stack limits, default name components and default attack range/piercing/charge
presence. Initialize the native component registry before reading item defaults. Compile
with the verified target classpath, then run `ExportInventoryFacts /absolute/path/facts.json`.
Verify the client and server exports agree before updating `data/inventory-facts.json` and
its hash/schema in `data/target.json` under `crates/java-protocol`. The generator checks
registry ordering and derives the runtime defaults table; component overrides/removals
still come from the authoritative server stack. Ordinary attacks may share Attack/Punch;
range, piercing and minimum-charge behaviors require their own implementation.

`NativeCooldownFixture.java` attaches to the same explicitly enabled isolated-server
bridge and invokes the real player's `ServerItemCooldowns` API. Build its JAR with
`Agent-Class: NativeCooldownFixture`, then run its main with `SERVER_PID agent.jar
/absolute/dedicated-request,FixturePlayer`. Commands `add 1..2400`, `remove`, `status`
and `detach` operate on the native cooldown group of that player's actual main hand.
This is server administration: the vanilla server emits the normal cooldown packets;
it does not fake a client use or successful interaction. Check timer expiry, menu/cursor
reconciliation and reconnect separately. A parsed timer is not a rendered cooldown overlay.
